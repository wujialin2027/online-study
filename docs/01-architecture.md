# 在线学习平台 · 架构说明

> 版本 v1.9（2026-11）｜适用于当前 `main` 分支
>
> 本文说明系统整体结构与关键设计决策，读者是接手维护的人或做技术评审的一方。
> 子系统细节见 `AI模块设计.md`，数据模型见 `表设计.md`，需求侧说明见 `需求分析.md`。
>
> **一句话概括**：一个 Spring Boot 单体应用，业务侧是课程 / 作业 / 论坛 / 审核，
> 在此之上挂了一个带双引擎、可切回旧链路、可度量效果并可核算成本的 AI 助教子系统。

## 2. 技术栈

| 层 | 选型 | 说明 |
|---|---|---|
| 运行时 | **Java 21** | 用 record、switch 表达式、文本块 |
| 框架 | **Spring Boot 4.1.2** | 父 POM 直管版本，不手写依赖版本号 |
| 安全 | **Spring Security 6** + JJWT 0.12.6 | 无状态 JWT，BCrypt 存密码 |
| 持久层 | **MyBatis-Plus 3.5.18** | `mybatis-plus-spring-boot4-starter`（Boot 4 需要专门的 starter） |
| 数据库 | **MySQL 8** | utf8mb4，InnoDB |
| AI 框架 | **Spring AI 2.0.2** | 仅新引擎使用，老引擎保留手写协议层 |
| 模型服务 | 阿里云百炼（OpenAI 兼容端点） | 对话 + 向量两个模型 |
| 前端 | Vue 3 + Vite 5 + Element Plus + ECharts | 单页应用，Nginx 托管静态文件 |
| 部署 | 阿里云轻量 2 核 2G + Nginx + systemd | 单机，无容器编排 |

**为什么是 Boot 4.1 而不是 3.x**：Spring AI 2.0 GA 硬要求 Boot 4.0/4.1 + Framework 7 + Jackson 3，
装不进 Boot 3.x（1.1.x 才配 Boot 3.5）。项目在改造时整体升到了 4.1.2，代价是四处破坏性变化
（`spring-boot-starter-aspectj`、MyBatis-Plus 要换 boot4 starter、Jackson 3 的包名从
`com.fasterxml` 变成 `tools.jackson`、`ObjectMapper` 变不可变对象），这些都已处理完毕。

## 3. 分层结构

```
online_study_backend/src/main/java/com/online/study/
├── config/          配置：Security、CORS、MyBatis-Plus、AI 属性与流式线程池
├── controller/      17 个 REST 控制器，只做参数校验 + 权限 + 转发
├── service/         业务逻辑（课程、报名、作业、审批、论坛）
│   └── impl/
├── ai/              ★ AI 子系统（见第 4、5 节）
│   └── engine/      双引擎实现
├── entity/          与表一一对应的实体
├── mapper/          MyBatis-Plus Mapper
├── vo/              对外响应对象（不直接暴露 entity）
├── common/          统一返回 Result、错误码 ResultCode
├── exception/       全局异常处理与业务异常
└── utils/           JWT、当前登录人、每日额度
```

三条分层约定：

1. **Controller 不写业务**。参数校验、`@PreAuthorize`、转发，三件事之外不做别的。
2. **不直接返回 entity**。所有对外结构走 `vo/`，避免"加一个数据库字段就自动暴露给前端"。
3. **业务异常统一走 `BizException` + `ResultCode`**，由全局处理器转成 `Result`。
   注意本系统**业务失败也返回 HTTP 200**，判定要看响应体的 `code`，这是前端拦截器的既定约定。

## 4. AI 子系统：双引擎架构

### 4.1 为什么同时存在两套引擎

`ai.engine` 有两个取值，改配置重启即切：

| 取值 | 实现 | 特点 |
|---|---|---|
| `legacy` | `LegacyAiEngine`，RestClient 直连 `/chat/completions`，自己解析 `tool_calls` | 2026-09 上线版，链路完全自己掌控 |
| `spring-ai` | `SpringAiEngine`，Spring AI 2.0 的 `ChatClient` + Advisor + `@Tool` | 2026-11 改造版 |

两套并存的三个理由：

1. **对照基线**。同一份 60 题评测集分别跑两套，才有"改造前 88% → 改造后 X%"这张表。
   删掉旧代码就永远失去对照组，效果只能靠嘴说。
2. **回退开关**。新引擎答歪了、服务商接口变了、演示前一晚出问题，改一行配置重启就回到能跑的状态。
3. **降级兜底**。新引擎初始化失败（Key 没配、依赖缺失）时自动落回 legacy，接口不返回 500。

### 4.2 一次问答的完整链路

```
用户提问
  │
  ├─ [1] 每日额度检查（按「账号+角色+自然日」计数，到量直接拒绝，不触发任何计费）
  ├─ [2] 身份确认为 JWT 中的登录人（不接受前端传 userId）
  │
  ├─ [3] 检索：问题向量化 → 与知识库全部块算余弦相似度 → 取 top-4 → 低于阈值丢弃
  │        （阈值 0.28；全被丢时至少保留最相关的一条）
  ├─ [4] 多轮记忆：从 ai_chat_message 取最近 5 轮问答，转成消息列表
  ├─ [5] 拼提示词：system 立规矩 + 历史 + 本轮问题（参考资料拼在用户消息里，不进 system）
  │
  ├─ [6] 调模型 ──┬─ 模型决定"翻小抄"（直接答） → 出答案
  │               └─ 模型决定"查数据库"（tool_calls）→ 执行工具 → 结果回填 → 再调模型（≤5 轮）
  │
  ├─ [7] 落库：提问 + 回答两条，带引擎、模型、token 用量
  └─ [8] 返回：答案 + 出处（含相似度百分比）+ 工具轨迹 + token
```

### 4.3 五个关键设计

**① 身份只从 JWT 取，接口不收 userId。**
工具的参数里没有 `studentId`。这不是靠每个实现自觉，而是接口签名上就没有这个口子
——"模型能不能查别人的数据"这个问题在架构层面不成立。

**② 工具按角色分对象，不靠 if 过滤。**
`StudentToolFunctions` 只声明学员那 3 个工具，`TeacherToolFunctions` 只声明教师那 3 个。
学员手里的对象上**物理没有**教师工具，模型连"有这个东西"都不知道。安全边界靠"看不见"，不靠"拦住"。

5 个工具名：`query_my_courses`、`query_my_homework`、`query_my_scores`（学员侧）、
`query_course_homework_stats`、`query_course_students`（教师侧）。

**③ 多轮记忆显式读库，不用框架的内存窗口。**
从 `ai_chat_message` 取最近 5 轮问答，裁成消息列表传给模型。没用 `MessageWindowChatMemory`，
原因是它默认是内存态（重启即丢），要落库得写适配层；而且工具调用的中间消息
（`AssistantMessage(toolCalls)`）会被记进历史表，污染回放。

**④ 向量落库，重启不丢。**
向量存在 `ai_vector_chunk` 表，启动时由 `DbVectorStore` 读进内存。只有库里一块都没有时
（首次部署 / 手动清表）才真的调向量接口重新灌库。写库走短事务整表替换，
**事务不横跨 embed 的 HTTP 调用** —— 否则一次外部调用超时就会连带锁住整张表。

**⑤ 流式是独立能力，不是接口的必选项。**
`AiStreamEngine` 是单独接口，legacy 不实现。服务层判不到该能力就把整段答案当一片推完再结束，
前端不用为两套引擎写两套渲染。

### 4.4 一次踩过的坑（留档，避免重复）

流式问答里学员被识别成教师。现象很有迷惑性：**同一轮问答落库的身份是正确的 `student/12`**，
但工具返回"该工具只对学员开放"。

根因是 `SecurityContextHolder` 基于 ThreadLocal：落库跑在业务线程，身份有效；
而工具是模型生成过程中被回调的，**跑在另一个线程**，ThreadLocal 为空，
空身份在"是不是学员"的三元判断里走了 else 分支。

修法是在工具对象的构造时（那时还在业务线程）把 `Authentication` 快照下来，
每次执行工具前绑回当前线程，执行完**还原而不是 clear**（线程池会复用线程，
clear 会把别人的上下文一起清掉）。`DelegatingSecurityContextExecutor` 只兜得住
"任务入口"，兜不住"任务内部又切了一次线程"。

## 5. 对外接口

| 方法 | 路径 | 权限 | 说明 |
|---|---|---|---|
| GET | `/ai/status` | 登录 | 知识库块数、维度、当前模型 |
| POST | `/ai/ask` | 登录 + 每日额度 | 一次问答，返回答案 + 出处 + 工具轨迹 + token |
| POST | `/ai/ask/stream` | 登录 + 每日额度 | 同上，SSE 流式，边生成边推送 |
| GET | `/ai/history` | 登录 | 我的历史对话（最近 50 条） |
| DELETE | `/ai/history` | 登录 | 清空我的历史 |
| POST | `/ai/knowledge/rebuild` | 管理员 / 教师 | 重建知识库 |
| POST | `/ai/knowledge/doc` | 管理员 / 教师 | 手工补充一段文字资料 |
| POST | `/ai/knowledge/doc/clear` | 管理员 / 教师 | 清空手工资料 |
| GET | `/ai/usage` | 管理员 / 教师 | 成本看板：token 与估算费用 |

**流式接口的约定**：`meta` 事件先到（知识块数、命中数），随后 `delta` 是正文增量片段，
最后一帧 `done` 带完整结果（含出处、工具轨迹、token）。`delta` 的内容包在 JSON 里，
因为 SSE 的 `data:` 按行切分，模型输出换行会把一条事件劈成两条。

## 6. 数据一致性

**报名防超卖**是这个系统里唯一有并发压力的写路径，做了四层：

| 层 | 手段 | 位置 |
|---|---|---|
| 1 | 原子占位：`UPDATE course SET enrolled = enrolled + 1 WHERE id = ? AND enrolled < capacity` | `CourseApplyServiceImpl` |
| 2 | 唯一索引兜底：`uk_student_course(student_id, course_id)` 防重复报名 | 建表语句 |
| 3 | 事务回滚退名额：后续步骤失败时把 `enrolled` 减回去 | `CourseApplyServiceImpl` |
| 4 | 状态校验：课程必须已审核通过且在报名期内 | `CourseApplyServiceImpl` |

单机 2 核环境下没有引入分布式锁 —— 第 1 层是单条 SQL，MySQL 行锁本身就保证原子性，
再加一层 Redis 锁只是增加故障点。

**AI 侧的一致性**：向量库重建走"先写库、再换内存引用"，中间失败时内存里仍是旧的完整快照，
不会出现"查到一个空知识库"。

## 7. 安全

| 项 | 做法 |
|---|---|
| 认证 | JWT（HS256），无状态；Token 过期由前端拦截器跳登录 |
| 授权 | 43 处 `@PreAuthorize`，方法级；另有路径级兜底规则 |
| 密码 | BCrypt |
| AI 工具越权 | 工具参数不含用户标识，身份一律从 JWT 取（见 4.3 ①） |
| AI 成本滥用 | 每日额度（账号+角色+自然日），到量在最前面就拒绝，连向量化都不触发 |
| 密钥 | `application.yml` 不入版本库，仓库里只保留全占位符的 `.example` |
| 提交前拦截 | Git hook 三道检查：顶层目录白名单、路径段黑名单、密钥/隐私/敏感措辞扫描 |

**改造前的一个事实**：`SecurityConfig` 的最后一行原本是 `anyRequest().permitAll()`，
相当于鉴权形同虚设。现在改成了按路径分组 + 方法级注解双层控制。

## 8. 可观测性与成本

三样东西：

1. **问答落库**（`ai_chat_message`）：每条回答记录引擎、模型、输入/输出 token。
2. **成本看板**（`GET /ai/usage`）：按天 / 按引擎 / 按模型三种维度聚合，
   用配置单价折算成金额。单价是配置项不是常量 —— 服务商调价、换模型时只改 yml 重启。
3. **工具轨迹**：每次问答返回 `usedTools`，能看到模型到底调了哪个工具、参数是什么、成功与否。
   排查"为什么答得不对"时，第一步就看这个。

**口径两条**（写进接口返回里，避免看的人自行脑补）：

- 只统计 `assistant` 行。一轮问答的输入 token 已经把提问算在里面，两边都算等于同一个问题收两次费。
- 金额是**线性折算的估算值**，不含缓存命中、阶梯价、免费额度抵扣。账单以服务商侧为准。

**一个实测数字**：60 题全量跑一轮约 17 万 token（输入 15 万 / 输出 2 万），
折算成本约 0.4 元。所以"这套 AI 一个月花多少钱"是可以算出来的，不是凭感觉。

## 9. 效果度量

用一套 60 题的评测集（真实课程名、真作业、真学员的提问方式），
两个引擎跑同一份题、同一个模型、同一个判分脚本。

| 指标 | legacy（基线） | spring-ai（当前） | 说明 |
|---|---|---|---|
| **答案正确性** | **90%**（53/59） | **90%**（53/59） | 关键词 / 数字 / 日期 / 拒答规则判定 |
| 单轮问答 | 91% | 86% | 60 题里除多轮组之外的部分 |
| 多轮表现 | 87% | 100% | 5 组 × 3 轮，含指代追踪 |
| 拒答边界 | 100% | 60% | 库外问题是否老实说不知道（见下） |
| 工具选择 | 100% | 100% | 25 题，期望工具是否被调用 |
| 检索召回 | 49% | 49% | 92 个关键点在引用片段中的命中比例 |
| 忠实度（代理） | 100% | 100% | 有引用或有工具轨迹即视为有依据 |
| 权限隔离 / 稳定性 | 未测 | 未测 | 60 题覆盖不到，留给专门的越权与重复性测试 |

**结论一句话**：新引擎在功能面完全追平旧引擎（答案正确性同为 90%、工具选择同为 100%），
多轮表现更好（100% vs 87%），**没有牺牲任何一项指标换框架**。

三条必须一起看的注脚：

1. **拒答 60% 不是行为退化**。5 道库外题里那条被判错的，模型实际回答是
   "现有资料里没有这个内容，无法查询"——语义上完全正确地拒答了，
   只是没有字面命中判分脚本的关键词表（它只认"没有相关 / 无法回答 / 不涉及 / 不提供"）。
   人工复核后应为 100%。**没有去改判分脚本**：一改，所有历史轮次的标签会一起漂移，
   新旧数字就不再可比，要改必须一次性重跑全部历史。这个取舍是刻意的。
2. **召回 49% 是两个引擎共同的天花板**，不是哪一个引擎的问题。它取决于资料切块方式与
   检索策略（纯向量、无重排），是下一步调优的主要目标。
3. **单轮 86% vs 91%** 的差主要落在"知识类问题"上，与召回率同源。

## 10. 部署

```
用户 ──► Nginx :80
          ├── /            → 前端静态文件（Vue 构建产物）
          ├── /api/        → 反向代理到 127.0.0.1:8081
          └── /uploads/    → 上传文件目录（不随 jar 重新部署覆盖）
                                    │
                            Spring Boot jar (:8081)
                                    │
                              MySQL 8 (:3306)
```

**三条部署纪律**（都踩过坑才定下来的）：

1. **`uploads/` 目录单独管理**，重新部署时只替换 jar 与前端产物，不动上传目录 ——
   否则每次上线都会把用户上传的作业附件清空。
2. **`proxy_pass` 末尾必须带 `/`**，否则 `/api/ai/ask` 会被原样转给后端（后端没有 `/api` 前缀），全部 404。
3. **不自动同步**。本地构建产物手动上传，避免"改了一半的代码被自动部署上去"。

服务器是 2 核 2G，内存账大致是：MySQL 约 400M、jar 堆约 512M、Nginx 与系统约 170M，
合计 1.1~1.5G。**这个配置装不下 Elasticsearch / Milvus 这类组件**（起步就 1G 以上），
所以混合检索只能走 MySQL 全文索引，向量检索只能自研 + 落 MySQL —— 这是环境约束下的取舍，
不是技术判断上的最优。

## 11. 已知限制

| 限制 | 影响 | 计划 |
|---|---|---|
| 检索只做纯向量，无关键词召回、无重排 | 专有名词类问题召回偏弱（当前 49%） | 切块重叠参数调优已在计划内；重排受内存限制暂不做 |
| 知识库数据来源只有"数据库 + 手工贴文字"，不支持上传文件 | 用户没法把自己的讲义灌进来 | 计划接入 Tika 做 PDF/Word 解析 |
| 单机部署，无容器编排 | 水平扩展要手工做 | 演示环境够用，不追求 |
| 评测集 60 题，覆盖不到越权与稳定性 | 这两项指标空缺 | 另有 40 条红队用例单独覆盖越权与提示注入 |
| 前端未接流式渲染 | 用户感受不到"边生成边出字" | 接口已就绪，前端接入是独立改动 |
